## Overview
Building a successful software product requires moving beyond assumptions. Just because users ask for a feature on Reddit does not mean they will use or pay for it.

---

## Core Product Validation Principles

```
┌────────────────────────────────────────────────────────┐
│ 1. Stop Building on Assumptions (0:00 - 0:50)          │
│    - Users have existing routines; switching is hard   │
├────────────────────────────────────────────────────────┤
│ 2. Observe Actual Behavior (0:53 - 1:50)               │
│    - Watch what users do, not what they say            │
├────────────────────────────────────────────────────────┤
│ 3. Prioritize Simplicity (3:26 - 4:38)                 │
│    - More features usually complicate rather than help │
├────────────────────────────────────────────────────────┤
│ 4. Launch Early to Gather Real Data (4:39 - 5:58)      │
│    - Launch is the start line, not the finish line     │
├────────────────────────────────────────────────────────┤
│ 5. Feature Prioritization Rubric (3:49 - 4:32)         │
│    - Request frequency across different users          │
│    - Personal utility (would you genuinely use it?)    │
│    - Impact vs. implementation complexity              │
└────────────────────────────────────────────────────────┘
```

## Tesler's Law (Conservation of Complexity)
> *"Complexity cannot be destroyed; it can only be relocated."*

- **Good Design:** The developer/system absorbs the complexity behind the scenes, making the user experience seamless.
- **Bad / Vibe-Coded Design:** The developer takes shortcuts, forcing the user to endure confusing menus, manual settings, and extra clicks.
